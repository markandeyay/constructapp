# FE-POLISH-1 Heavy-Tier UX Audit

Date: 2026-06-06
Branch: `phase4-polish`
Scope: application-layer frontend UX under `apps/web`, with API contract references only as needed.

## Journey Covered

- Landing page and initial workspace affordance.
- First design prompt submission.
- Job polling and loading behavior.
- Design result display.
- Clarification question and answer turn.
- Refinement turn.
- Validation report display.
- Plasmid map rendering, including small/mobile viewport behavior.
- Export flow.

## Findings

### 1. Validation report is present in the contract but not visible in the UI

- Severity: Critical
- User-visible impact: A researcher can receive a completed design without seeing whether validation passed, warned, or failed. This hides the most important trust/safety signal and makes failed or warning checks indistinguishable from a clean recommendation.
- Evidence: `apps/web/lib/types.ts:46-56` includes `validation_report` on `JobResultPayload`; `packages/application/sessions.py:44-53` includes `validation_report` in the application job result; sample eval payloads contain `overall`, `checks`, and `generated_by_model_version` at `data/eval/generation/2026-06-05-230925-generation-eval.json:125-136`. The chat result renderer in `apps/web/app/page.tsx:142-152` only displays message text and retrieved templates.
- Recommended fix: Add a readable validation summary card to each assistant result that has a report. Show overall status first, then grouped checks with status badges, messages, and any region coordinates. Use compact styling in chat and consider a detailed panel in the right rail.
- Requires API contract changes: No for the current shape shown in `validation_report`; Yes only if the product needs severity levels, remediation text, or check categories beyond `status` and `message`.

### 2. Polling/loading feedback is too thin and can end in a confusing timeout

- Severity: High
- User-visible impact: After submit, the only visible progress is a disabled button labeled `Working` and a raw `Polling job {id}` line. There is no staged progress, elapsed time, retry context, or explanation that generation may take time. If the 30-second timeout hits, the user sees a technical timeout rather than a recoverable in-progress state.
- Evidence: Submit disables input during `submitting`/`polling` at `apps/web/app/page.tsx:166-181`; active job display is only `Polling job {activeJobId}` at `apps/web/app/page.tsx:183`; `pollJob` uses a fixed 750 ms interval and throws after 30 seconds at `apps/web/lib/api.ts:33-48`.
- Recommended fix: Replace raw job ID polling text with a visible loading card in the conversation: queued, designing, validating, rendering, with elapsed time and a non-technical fallback after timeout. Consider keeping the job ID in a collapsible/debug detail.
- Requires API contract changes: Maybe. Better stage labels require backend job phases or progress metadata; a UI-only improvement can still show generic elapsed-time states.

### 3. Export has no loading, success, or error feedback

- Severity: High
- User-visible impact: Clicking `GenBank` or `FASTA` produces no visible in-progress state, no success confirmation, and no error message. Slow or failed downloads look like a dead click, and repeated clicks can dispatch duplicate export requests.
- Evidence: Export buttons call `void onExport(...)` without local status handling at `apps/web/components/export-actions.tsx:18-30`; `handleExport` awaits `exportDesign` and triggers a download but catches no errors and updates no UI state at `apps/web/app/page.tsx:100-114`; `exportDesign` throws `ApiError` on non-OK responses at `apps/web/lib/api.ts:51-56`.
- Recommended fix: Track per-format export state, disable the active button during download, show `Preparing...`, `Downloaded`, and an inline error with retry guidance. Surface server-supplied filenames if contractually preferred.
- Requires API contract changes: No for basic progress/errors. Maybe if the UI should use `Content-Disposition` filenames or support asynchronous export jobs.

### 4. Mobile and small viewport layout makes the map hard to use

- Severity: High
- User-visible impact: On small screens, the map appears after a full-height chat section, uses a fixed 520 px map height, and the right rail also has `min-h-screen`. Users may need to scroll past an entire chat viewport to see the design, while the map itself can be clipped or cramped with SeqViz controls.
- Evidence: The main layout stacks to one column but keeps both sections at `min-h-screen` in `apps/web/app/page.tsx:117-191`; the plasmid map container uses fixed `h-[520px]` and `overflow-hidden` at `apps/web/components/plasmid-map-view.tsx:57-58`; the empty map state is `h-96` at `apps/web/components/plasmid-map-view.tsx:21`.
- Recommended fix: Add responsive heights and navigation affordances. On mobile, shorten the initial chat/map panels, add a `View map` jump after result completion, allow horizontal/vertical map overflow where SeqViz needs it, and test at 375 px and 768 px widths.
- Requires API contract changes: No.

### 5. Clarification and refinement turns are not visually distinct enough from normal refinement

- Severity: Medium
- User-visible impact: The same `/refine` endpoint and input area are used for both clarification answers and later design refinements. The placeholder changes, but there is no persistent cue that the next response must answer a specific question, and the submit logic has a redundant branch that does not encode answer-vs-refine semantics.
- Evidence: Clarification state changes placeholder and button text at `apps/web/app/page.tsx:169-181`; both clarification answers and refinements call `submitRefinement` at `apps/web/app/page.tsx:60-65`; clarification detection accepts `clarification_question` from either result root or `design_spec` at `apps/web/app/page.tsx:210-214`.
- Recommended fix: Pin the active clarification question above the composer, label the composer as `Answer clarification`, and after the answer is submitted render a clear `Answer submitted` user turn. If the backend needs to distinguish clarification answers from general refinements, introduce an explicit action/field rather than overloading refine.
- Requires API contract changes: Maybe, if answer-vs-refinement semantics matter to downstream session handling.

### 6. API errors are surfaced as raw backend text and can be noisy or unreadable

- Severity: Medium
- User-visible impact: 422, 404, timeout, failed job, CORS/network, and export failures are not translated into clear recovery actions. Backend validation bodies can render as raw JSON strings in the chat, and export errors are not shown at all.
- Evidence: `request` throws the raw response body or status string at `apps/web/lib/api.ts:67-70`; submit catches errors and appends the message verbatim at `apps/web/app/page.tsx:88-94`; export has no catch path at `apps/web/app/page.tsx:100-114`.
- Recommended fix: Normalize API errors into friendly titles and actionable copy. Keep raw details in a collapsed section. Use specific messages for missing session, malformed prompt, job timeout, failed generation, and export failure.
- Requires API contract changes: Maybe. Best UX would use structured error codes/details from the API; current UI can still map status/body heuristically.

### 7. Landing page starts with a prefilled prompt, which can obscure the primary action

- Severity: Medium
- User-visible impact: The textarea is already filled with an example design. A first-time user may click `Design` unintentionally or miss that they can replace it. The workspace also lacks examples, constraints guidance, or expected timing near the composer.
- Evidence: `DEFAULT_PROMPT` is assigned directly to input state at `apps/web/app/page.tsx:19-33`; the welcome message gives high-level pipeline copy but no prompt guidance at `apps/web/app/page.tsx:24-30`.
- Recommended fix: Move the default prompt into example chips or a placeholder, keep the textarea empty, and add concise guidance for useful inputs such as host, marker, promoter, payload, constraints, and safety limitations.
- Requires API contract changes: No.

### 8. Result summary can report success even when no map or validation details are available

- Severity: Medium
- User-visible impact: If a job completes without `annotated_sequence`, the UI says the job completed and asks the user to review templates/validation details, but validation details are not rendered and the map remains in its empty state. This is a confusing silent partial-result state.
- Evidence: `resultSummary` returns `Design job completed. Review the returned templates and validation details.` when no sequence is present at `apps/web/app/page.tsx:217-226`; `annotatedSequence` is the only input to the map at `apps/web/app/page.tsx:36-41` and `apps/web/app/page.tsx:189`; validation is not displayed in the message renderer at `apps/web/app/page.tsx:142-152`.
- Recommended fix: Treat completed-without-sequence as a partial result. Show what was returned, what is missing, and whether retry/refine is recommended. If validation exists without a sequence, still render validation.
- Requires API contract changes: Maybe, if the UI needs an explicit partial-result reason or recovery hint.

### 9. SeqViz rendering lacks an error/empty fallback for malformed or extreme annotation data

- Severity: Medium
- User-visible impact: A malformed annotation range, huge sequence, unknown topology, or SeqViz runtime failure can leave the right panel blank/broken. Users receive no explanation or fallback sequence/feature table.
- Evidence: Feature annotations are passed directly from API data into SeqViz at `apps/web/components/plasmid-map-view.tsx:28-35` and `apps/web/components/plasmid-map-view.tsx:59-66`; the only loading fallback is for dynamic import at `apps/web/components/plasmid-map-view.tsx:7-10`; feature legend clamps display coordinates but SeqViz input itself is not clamped at `apps/web/components/plasmid-map-view.tsx:86-95`.
- Recommended fix: Add defensive validation for display-only map inputs, an error boundary/fallback for map render failures, and a sequence/feature table fallback. Log or surface invalid feature ranges without crashing the whole result.
- Requires API contract changes: No for defensive UI. Maybe if backend should guarantee coordinate conventions and topology enum values in the documented contract.

### 10. Retrieved template evidence is terse and not actionable

- Severity: Low
- User-visible impact: The UI shows only up to three template names and scores without matched fields, source, or why they matter. Users cannot evaluate grounding quality from the visible result.
- Evidence: Retrieved template rendering slices to three and displays name/source_id/score only at `apps/web/app/page.tsx:143-151`; `RetrievedTemplate` includes optional `source` and `vector_profile` but not matched fields in the frontend type at `apps/web/lib/types.ts:38-44`.
- Recommended fix: Add a compact evidence section with template identity, vector profile, source, score explanation, and matched fields if available. Keep long details collapsible.
- Requires API contract changes: Maybe, if matched fields or rationale should be part of the formal web contract.

## Questions for the Human

- Should clarification answers remain `/refine` requests, or should the API expose a separate clarification-answer action so the UI can label and persist the turn differently?
- Should job polling expose phase/progress fields such as `queued`, `retrieving`, `designing`, `validating`, and `persisting`, or should the frontend use generic elapsed-time loading copy only?
- What validation report shape is considered stable for the web UI: only `overall/checks/generated_by_model_version`, or should severity, category, remediation, and affected feature IDs be added before investing in a richer report view?
- Should export filenames come from the API `Content-Disposition` header, or should the frontend continue generating names from `design_id` and format?
- On mobile, should the map become a separate tab/drawer below the chat, or should the current stacked layout be preserved with jump links and responsive heights?
- Should completed jobs without `annotated_sequence` be treated as successful partial results, failures, or clarification-like states requiring another user turn?
