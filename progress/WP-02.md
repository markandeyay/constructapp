# WP-02: capability contract, capability registry, AAV part registry, shared sequence utilities

Agent: wp02-contract. Status: done.

## Contract decisions (packages/core/schemas/capability.py)

- Field names and types follow section 5.1 literally. One field was added at the coordinator's
  instruction: `CheckResult.remediation: list[str] | None = None`. Rationale: section 9.3 requires
  `must_also_report: ["remediation_suggestion"]`, section 6.5 requires the packaging-limit FAIL to
  carry a specific substitution, and section 6.6 mandates the remediation engine, but section 5.1 has
  no place for structured remediation. The human readable substitution text must still be in
  `message` (section 5.4 rule 2). The field only lets the gold harness assert remediation
  structurally. It is not a new check_id, because section 6.4 forbids inventing checks.
- Models derive from `SchemaModel` (existing convention: pydantic v2, `extra="forbid"`) through a
  small `CapabilityModel` base that sets `use_enum_values=False`, so `Severity` and `CapabilityKind`
  fields stay enum members as typed in the spec. They compare equal to their strings and dump to
  plain values in JSON.
- Rule 1: `worst_severity` and `overall_from_checks` compute `overall`. UNKNOWN is unranked, so it
  never improves a verdict. A report with no evaluable check is UNKNOWN, never PASS. A
  `ValidationReport` whose `overall` disagrees with its checks is rejected, and
  `ValidationReport.from_checks` builds one correctly. Duplicate `check_id` in one report is rejected.
  `unknown_checks` lists the unevaluated checks for the UI.
- Rule 3: `DesignResult.parameters_used` must be non-empty.
- Rule 4: `thresholds_fingerprint` (SHA-256 of canonical JSON) and `assert_version_matches_thresholds`.
  A capability keeps a table `{validator_version: fingerprint}` beside its constants and calls the
  assertion from a test. A threshold edited without a version bump fails.
- Rule 5: `DesignResult.provenance` must be non-empty with no blank entries. A user supplied sequence
  is recorded as `user_input:<field>`.
- Rule 2 (actionable messages) cannot be checked by code, it stays a review obligation.
- `CheckResult.coordinates` use the existing `FeatureRegion` convention: zero-based, end exclusive.
- `CapabilityGenerator` and `CapabilityValidator` are `runtime_checkable` Protocols.

## Capability registry (packages/core/capability_registry.py)

At the first path the gold runner searches. Contains `CapabilitySpec`, `PLASMID_SPEC`,
`CAPABILITY_REGISTRY` with the three delimited regions reproduced character for character from
section 13.3, plus `get_capability`, `list_capabilities`, `resolve_reference`.

`CapabilitySpec` exposes what the gold runner needs: a `validator_factory()` method (built from the
dotted path `validator_ref`, a zero-argument callable returning a CapabilityValidator) and a
`design_model` property (resolved from `design_model_ref`). Code is referenced by dotted path, never
imported at registration, so there are no import cycles. A capability writes one inline
`CapabilityKind.X: CapabilitySpec(...)` expression inside its own region and needs no import line.
PLASMID_SPEC registers no `validator_ref`: the existing plasmid engine has the original interface, so
gold cases for plasmid report unevaluable until an adapter exists (outside WP-02).

Router include block: `services/api/routes/__init__.py` with the same three regions inside
`CAPABILITY_ROUTERS`, entries `RouterInclude(capability, "package.module:attribute", prefix)`, and
`include_capability_routers(app)`. It is not yet called from `services/api/app.py`, which WP-02 does
not own (cross-WP request filed).

## Part registry (data/parts, packages/core/part_registry.py)

14 parts shipped, 1 spec-listed part not shipped. Record fields are exactly those of section 4.3 plus
a `provenance` object (accession, record title, feature type and note, coordinates, strand, retrieval
date and method). `tissue_specificity` uses the AAVRequest `target_tissue` vocabulary and is
`"ubiquitous"` for ubiquitous promoters (the section 4.3 example shows null for CMV, but the request
schema has a `ubiquitous` target, so an explicit value avoids ambiguity). It is null for non-promoters.
The loader rejects non-ACGT sequences, length mismatches, id/path mismatches, missing source or
citation, and unknown tissue values.

`data/parts/build_parts.py --write | --verify` regenerates or checks every record from NCBI.
`CONSTRUCT_VERIFY_PARTS=1 python -m pytest tests/parts` runs `--verify` (passed, 14 of 14 matched).

## Shared utilities (packages/core/sequence)

`dna` (clean_sequence, complement, reverse_complement, gc_content, IUPAC table), `codon` (NCBI genetic
code tables 1 and 11 checked against Biopython's copy, translate, find_orfs, synonymous codons; no
host codon usage table is bundled, a caller must source one), `search` (find_exact incl. circular,
find_both_strands, find_with_mismatches, find_iupac, homopolymer_runs, direct_repeats), `align`
(Needleman-Wunsch, Smith-Waterman, edit_distance, global_identity). The nearest-neighbor Tm is not
here (WP-04 owns it). Thresholds, lengths, mismatch counts and alignment scores are required
arguments, never silent defaults; `UNIT_COST_SCORING` is documented as a convention with no
biological meaning.

## Configurable thresholds introduced

None. WP-02 added no biological threshold. Every length, tolerance and score in the utilities is a
required caller argument. Section 6.5 constants belong to WP-03.
