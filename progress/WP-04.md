## 1. The Appendix A.1 verification gate (section 14.2)

### Reference tool and exact configuration

| Item | Value |
|---|---|
| Tool | Biopython, `Bio.SeqUtils.MeltingTemp.Tm_NN` |
| Version | **1.87** |
| Nearest-neighbor table | `nn_table=mt.DNA_NN3` |
| Salt correction | `saltcorr=5` |
| Monovalent salt | `Na=50` (mM) |
| Divalent, dNTP | `Mg=0`, `dNTPs=0` |
| Strand concentration, non-self-complementary oligo | `dnac1=250, dnac2=250, selfcomp=False` |
| Strand concentration, self-complementary oligo | `dnac1=500, dnac2=0, selfcomp=True` |
| Conditions | 500 nM total strand, 50 mM monovalent salt (Appendix A.1) |
| Tolerance | 1.0 degree C (section 14.2), never widened |

### Why this Biopython configuration corresponds to Appendix A

This mattered more than anything else in the package, because comparing against
the wrong table produces a phantom discrepancy that tempts you to change your own
code. Biopython ships four DNA nearest-neighbor tables. `DNA_NN3` is the one whose
values are Appendix A's:

* its ten nearest-neighbor pairs are Appendix A's ten, value for value;
* `init_A/T` is `(2.3, 4.1)`, Appendix A's "Initiation with terminal A.T";
* `init_G/C` is `(0.1, -2.8)`, Appendix A's "Initiation with terminal G.C";
* `sym` is `(0.0, -1.4)`, Appendix A's symmetry correction;
* the general `init` term and the three other initiation slots are all `(0, 0)`,
  so Appendix A's two terminal terms are the whole initiation story and nothing
  extra is silently added.

`DNA_NN1` (Breslauer), `DNA_NN2` (Sugimoto) and `DNA_NN4` (SantaLucia and Hicks
2004) all differ in the initiation terms and would have given a reference several
degrees away. `DNA_NN4`'s init is `(0.2, -5.7)` and its `init_A/T` is `(2.2, 6.9)`,
which is the near-miss most likely to be picked by mistake.

`saltcorr=5` is documented by Biopython as
"Correction for deltaS: 0.368 x (N-1) x ln[Na+] (SantaLucia (1998))", which is
Appendix A's salt correction formula character for character, applied to the
entropy rather than to the temperature.

The strand concentration term needed care. Biopython uses `k = dnac1 - dnac2/2`
normally and `k = dnac1` when `selfcomp` is set. Section 7.3 uses `C_T / 4` for a
non-self-complementary duplex and `C_T` for a self-complementary one. So a total
strand concentration of 500 nM is passed as `dnac1 = dnac2 = 250` in the first
case, giving `k = 250 - 125 = 125 nM = C_T/4`, and as `dnac1 = 500` with
`selfcomp=True` in the second, giving `k = 500 nM = C_T`. Both describe the same
500 nM of total strand, which is the Appendix A.1 condition.

`tests/assembly/test_tm_reference.py::test_reference_table_matches_appendix_a`
asserts every one of those table facts, so a future Biopython release that
changed a value fails the test instead of silently moving the reference.

Two of the four Appendix A.1 oligos are self-complementary, so the symmetry

## 3. The magnesium and dNTP conversion (section 7.3)

Section 7.3: "If magnesium and dNTPs are specified, convert to a monovalent
equivalent before applying this; record which conversion was used in the docstring
with its source."

**Conversion used:** von Ahsen N, Wittwer CT, Schutz E. "Oligonucleotide melting
temperatures under PCR conditions: nearest-neighbor corrections for Mg2+,
deoxynucleotide triphosphate, and dimethyl sulfoxide concentrations with
comparison to alternative empirical formulas." Clin Chem 2001;47(11):1956-1961.

```
[Na_eq] = [Na+] + 120 * sqrt([Mg2+] - [dNTP])      when [dNTP] < [Mg2+]
[Na_eq] = [Na+]                                    otherwise
```

All concentrations in mM. The second line is not a simplification: dNTPs chelate
magnesium, so when dNTPs are at or above the magnesium concentration there is no
free magnesium left to contribute, and the divalent term is dropped rather than
extrapolated into a region the formula does not cover.

Why this conversion and not another: it is the conversion the reference tool
applies. Biopython's `salt_correction` builds the identical sodium equivalent and
cites the same paper, and Primer3 applies the same formula in
`divalent_to_monovalent`. Using the same conversion as the reference tool is what
keeps the Appendix A.1 comparison a comparison of like with like, and
`test_tm.py::test_divalent_conversion_matches_the_reference_tool` checks the two
agree at the section 7.2 default conditions (1.5 mM Mg, 0.2 mM dNTP) rather than
checking that the formula was typed in correctly.

Appendix E points at the Owczarzy treatments for mixed-ion conditions. Those are
not implemented: Biopython exposes Owczarzy 2008 as `saltcorr=7`, which corrects
`1/Tm` rather than the entropy and therefore cannot be combined with Appendix A's
entropy correction without choosing between the two. Appendix A specifies the
entropy correction, so that is what is implemented, with the von Ahsen monovalent
equivalent feeding it.

Both facts reach the user: `parameters_used` carries `sodium_equivalent_mm`, the
full citation under `divalent_conversion`, and the explicit text
"not applied: dNTP concentration is at or above the magnesium concentration" when
the divalent term was dropped. Nothing degrades silently.

## 4. Open question Q6: ViennaRNA

**Decision: ViennaRNA is installable and is preferred, as section 7.4 and Q6
direct. It is an optional dependency with a documented, labelled fallback.**

* Checked rather than assumed. `python -m pip install ViennaRNA` succeeded in this
  environment and installed **ViennaRNA 2.7.2** (importable as `RNA`).
* **DNA parameters are loaded explicitly.** ViennaRNA defaults to RNA stacking
  parameters. A primer is DNA, and folding it against RNA parameters would report
  the wrong free energy with no warning, so
  `RNA.params_load_DNA_Mathews2004()` is called before any fold. That is the DNA
  parameter set ViennaRNA distributes as `dna_mathews2004.par`.
* It is imported lazily and cached, so the engine choice is fixed for the life of
  a process and two validations in one run cannot disagree about it.
* It is **not** added to `requirements.txt`, which WP-04 does not own. Filed as a
  cross-WP request. Until it is added, an environment without it uses the
  documented fallback, which is the Q6 default and is honest rather than broken.
* Which engine ran is never left to the reader. `HairpinResult.engine` is
  `viennarna_dna_mathews2004` or `sliding_window_stem_bp`; the check message names
  the metric and its units; `parameters_used` carries
  `hairpin_engine_requested` and `hairpin_engine_available`.
* `hairpin_engine` on the request pins the engine to `auto`, `viennarna` or
  `window`. The tests pin it, so they are deterministic regardless of the
  environment they run in, and both engines are covered.
* Requesting `viennarna` where it is absent returns the `primer.hairpin` check as
  **UNKNOWN with a reason**, never a pass (section 3.3 constraint 4).

## 5. Dimer and hairpin scoring, documented (section 7.4)

Section 7.4 permits a sliding-window complementarity score with explicit 3'
weighting "provided the scoring is documented". Here it is. Full text is in the
`packages/validation/assembly/structure.py` module docstring; each claim below is
asserted by a test in `tests/assembly/test_structure.py`.

### Why 3' involvement is scored separately

Section 7.4: "3' end involvement is what matters, because a 3' dimer is extendable
and produces primer-dimer artifact that consumes the reaction." Every function
reports two numbers and the thresholds for the two are separate.

### The complementarity score (checks 7 and 8, and the hairpin fallback)

Units are base pairs. Two oligos are scanned at every relative offset, the second
read in reverse so that bases which would pair sit opposite each other. Only
Watson-Crick pairs count: an ambiguity code never pairs, because treating it as a
wildcard would over- or understate structure with no way for the reader to tell
which.

* **`any_score`**: the best gapless local score over all offsets, a complementary
  position scoring +1 and a non-complementary one -1, taking the best contiguous
  stretch within the overlap. Same construction and same units as Primer3's
  `PRIMER_MAX_SELF_ANY` and `PRIMER_PAIR_MAX_COMPL_ANY`, whose defaults of 8.00
  are the thresholds used.
* **`three_prime_score`**: the longest run of consecutive complementary base pairs
  that includes the 3'-terminal base of the query, maximised over offsets, in base
  pairs. An offset where the 3'-terminal base is not itself paired scores zero,
  because an unpaired 3' terminus is not extendable. This is the explicit 3'
  weighting. Thresholds are Primer3's `PRIMER_MAX_SELF_END` and
  `PRIMER_PAIR_MAX_COMPL_END` defaults of 3.00, same units.
* For a hetero-dimer, **both** primers' 3' ends are tested and the worse is
  reported, with `three_prime_partner` naming which. Either extendable 3' end
  consumes the reaction.

Honesty note, recorded for WP-10: the numbers are in Primer3's units but are not
guaranteed identical to Primer3's own output, because Primer3's alignment
implementation differs in detail and the 3' definition here is a contiguous
anchored run rather than a local alignment score. The definition actually used is
in `parameters_used` under `dimer_score_definition`, so nothing claims to be
Primer3's output.

A gapless scan is used rather than WP-02's shared `local_align`, deliberately:
`local_align` admits gaps and has no 3' anchoring, and an extendable 3' dimer is a
contiguous duplex, not a gapped alignment.

### The hairpin score

With ViennaRNA: minimum free energy in kcal/mol at ViennaRNA's default 37 C under
the DNA parameters, plus the dot-bracket structure. 3' involvement is any paired
position inside the 3'-terminal window.

Without it: the longest contiguous complementary stem closing a loop of at least
`HAIRPIN_MIN_LOOP_NT` (3 nt, the standard nucleic acid secondary structure
minimum and ViennaRNA's own minimum), reported in base pairs.
`delta_g_kcal_per_mol` is **None** in this mode, not an estimate: reporting a free
energy that was not computed would be an invented number.

## 6. Codon table decision (section 7.6, Appendix E)

**Decision: no host codon usage table is bundled. The frequency comparison is
reported as UNKNOWN with a reason. No frequency is invented.**

WP-02 could not source one and WP-04 did not either. A codon usage table is 64
frequencies per host, and section 3.3 constraint 1 forbids writing numbers down
from memory. A fabricated table is worse than none, because it would make the
domestication report look authoritative while recommending the wrong codon.

What that means in practice, and what is **not** degraded:

1. The silent substitution search runs fully. Every edit it returns destroys the
   recognition site and preserves the amino acid, which is the part of section 7.6
   that is a correctness requirement, and both properties are asserted by
   re-translating the edited sequence in `test_domestication.py`.
2. Codon choice falls back to the **minimal silent edit**: among the synonymous
   codons that destroy the site, the one differing from the original in the fewest
   nucleotide positions, ties broken by sort order so the result is deterministic.
   Section 7.6 names the minimal edit as the correct rule outside a coding
   sequence; it is the rule inside one too when the host preference is
   unavailable.
3. The host frequency is `host_frequency_status="unknown"` with
   `host_frequency_reason` giving the reason, on every edit, and the same statement
   appears in the report notes, in the `gg.enzyme_site_internal` message, and in
   `parameters_used`. It is never a number and never omitted.

The mechanism is implemented and tested, so sourcing a table later is a data
change and not a code change. A caller supplies `HostCodonUsageSpec` with a host
and a mandatory citation; a table without a citation is refused at construction,
per Appendix E's "name the table and the host". With a table, the preference is
applied (highest host frequency among the minimal-edit candidates) and both
frequencies are reported with the table named.

## 7. Published overhang standard decision (Appendix D)

**Decision: the mechanism ships, no published standard's overhang set does.**

Appendix D: "If the assembly follows a published modular standard, use that
standard's defined overhang set rather than generating overhangs, and cite the
standard." The mechanism is `OverhangStandardSpec` on the request, and when one is
supplied its overhangs are used verbatim in place of generated ones, the citation
is carried into `provenance` and `parameters_used`, and `Junction.overhang_source`
records `overhang_standard` rather than `fragment_junction`.

`BUNDLED_OVERHANG_STANDARDS` is empty. Neither the MoClo fusion site set (Weber et
al. 2011) nor any other standard's 4 bp overhang strings could be read from a
primary document while this package was built, and section 3.3 constraint 1
forbids reciting sequence from memory: a wrong 4 bp overhang set produces an
assembly that silently does not assemble. With no standard supplied, the overhang
is the first 4 nt of the downstream fragment, which is the scarless choice, and
the design says that is what it did rather than claiming to follow a standard it
does not have.

### Applicability, and why an inapplicable check is omitted rather than passed

Nine checks are strategy-specific: 11 to 13 are Gibson, 14 to 17 are Golden Gate,
18 needs a junction topology to examine. A check that does not apply is **omitted**
from the report. Reporting it PASS would assert something that was never tested,
which section 3.3 constraint 4 forbids; reporting it UNKNOWN would put a permanent
unevaluated row in every report, which section 5.4 rule 1 reserves for checks that
genuinely could not be evaluated, and would make every Tier A case impossible.
`parameters_used` carries `applicable_checks`, `checks_evaluated`,
`checks_not_evaluated` and the reason, so a reader can always see what was not
examined. **This is a judgment call and is flagged for WP-10.**

Each check produces at most one `CheckResult`, aggregating across the primers,
junctions or amplicons it inspects, and the message names every contributing item
with its number. That is required rather than stylistic: the shared contract
rejects two results with the same `check_id` in one report.

## 10. Other judgment calls, for WP-10

Named explicitly, each one a place where the spec left a choice.

1. **Tm is measured on the template-binding region, not the whole oligo.** A Gibson
   homology arm or a Type IIS tail does not anneal to the template in the first
   cycle, so including it would report a temperature the reaction never sees. The
   order table says so in the notes column of every tailed primer, and
   `parameters_used` carries `tm_measured_on`.
2. **Check 4 measures two lengths.** The binding region against the Primer3 window,
   the whole oligo against an ordering limit. Measuring the whole oligo against 27
   nt would fire on every correct Gibson or Golden Gate design.
3. **Check 15 treats an overhang and another's reverse complement as not distinct.**
   Appendix D says "all overhangs in one assembly distinct". A reverse-complement
   collision lets a fragment ligate into the wrong junction backwards, which is the
   same hazard, so it is reported under the same check with a message that
   distinguishes the two cases.
4. **Check 18 identifies a junction by its joining sequence.** A fusion overhang for
   Golden Gate, a homology arm for Gibson, a restriction site for PCR cloning. One
   distinct sequence per junction means exactly one order. A consequence worth
   noting: simple PCR cloning with one enzyme at both ends fails check 18, which is
   correct, since the insert really can go in either orientation.
5. **Golden Gate overhangs are taken from the downstream fragment's own first bases**
   when no standard is supplied. That is the scarless choice. A supplied standard
   overrides it entirely.
6. **Spacer and filler nucleotides in a Type IIS tail** are chosen by exhaustive scan
   in A, C, G, T order, taking the first base that adds no new recognition site. The
   order carries no biological claim; it exists for determinism.
7. **The validator composes a design that arrives without primers**, using the same
   deterministic designer the generator uses, and records that it did so. This is
   what lets a gold case supply fragments only (for a fragment-level check) or pin
   exact primers (for a primer-level check). Both are needed and section 9.4 asks
   for both kinds.
8. **Domestication rejects an edit that trades one site for another.** The whole
   fragment is rescanned on both strands after each candidate edit and the site
   count must go down, not sideways.
9. **Test fixture sequences are slices of real GenBank records** already in this
   repository's part registry (KU341333.1, the CBh promoter, and AF396260.1, the
   CMV promoter), at recorded offsets. The slice offsets are chosen, the sequence is
   not. Choosing where to cut is the only freedom a Gibson or Golden Gate primer
   design has, because the primer must start exactly at the junction or bases are
   lost from the construct.
