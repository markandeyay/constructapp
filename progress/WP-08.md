## 1. THE SENTENCE THAT MAY BE CLAIMED

Section 11.2 states the allowed wording for the case that actually shipped, and
the case that shipped is exactly the one it describes: a provenance check, a
screening hook and an audit log, with no external screening backend configured.
So the claim is this sentence, and WP-11 and the pitch may quote it verbatim:

> **Designs are composed only from curated parts, every base is attributable,
> and exports are logged.**

Three elaborations are also true and may be used alongside it, each of which is
a property a test in `tests/screening/` defends:

> A design containing sequence that traces to no curated part, no retrieved
> record, no user supplied input and no named rule is blocked from export, not
> warned about.

> Every export, permitted or blocked, writes one audit entry recording what was
> exported, when, the validator version and the screening result.

> No external sequence screening backend is configured in this build, and every
> audit entry says so in a plain boolean and in a sentence.

### What may NOT be said

Per section 16's row on claims about section 11, and per the Q8 default:

* Not that any sequence was screened, examined, checked or cleared against any
  external criterion. Nothing external examined any design. No backend is
  wired. There is no finding to report and no absence of findings to report.
* Not the specific phrase section 11.2 and section 16 each single out as
  forbidden absent a wired backend, and not any paraphrase of it. That phrase is
  deliberately not reproduced in this file, so that no line of this file can be
  quoted as though it were the claim. Read it in section 11.2 of the
  specification. The hook exists, the interface is documented, the backend slot
  is empty, and the emptiness is recorded in every entry.
* Not that the provenance assertion is a judgement about what a sequence does.
  It is a composition and attribution property: where each base came from. It
  says nothing about function, and `composition.py` states that limit in its
  own module docstring.
* Not that the gate runs on every export path in the product today. It runs on
  every export that goes through `export_screened_design`. Section 6 of this
  file lists exactly which capabilities reach it and which do not, and why.

## 2. THE SCREENING INTERFACE

`packages/application/screening/backends.py`.

```python
@runtime_checkable
class ScreeningBackend(Protocol):
    backend_id: str
    backend_version: str

    def screen(self, subject: ExportSubject) -> ScreeningResult: ...
```

### What a backend receives

`ExportSubject` (`attribution.py`) carries everything about one design:

| Field | What it is |
|---|---|
| `capability` | `CapabilityKind`: aav, assembly, guide_rna, plasmid |
| `design_id` | the design's own id |
| `validator_version` | the capability's `ValidationReport.validator_version` |
| `sequences` | one `AttributedSequence` per exported sequence: `name`, `sequence` (A, C, G, T only, upper case), `segments`, `role` |
| `declared_provenance` | the design's `DesignResult.provenance`, verbatim |
| `adapter` | which adapter built this subject |

`subject.total_bp` is the total submitted. `subject.sequence(name)` looks one
up. A backend must not mutate the subject.

### What a backend returns

```python
ScreeningResult(
    backend_id="...",            # identifies the service
    backend_version="...",       # identifies its version, so a stored entry stays interpretable
    outcome=BackendOutcome...,   # see the table below
    findings=[BackendFinding(sequence_name=..., code=..., detail=..., start=None, end=None)],
    detail="one sentence a person will read in an audit log",
    sequences_submitted=len(subject.sequences),
    bases_submitted=subject.total_bp,
)
```

`BackendOutcome` has five values and the split between them is the whole point
of the naming:

| Value | Meaning | `external_screening_ran` |
|---|---|---|
| `no_external_screening_ran` | no backend is configured | `False` |
| `backend_unreachable_not_screened` | a backend is configured and could not be reached | `False` |
| `backend_error_not_screened` | a backend is configured and failed | `False` |
| `backend_reported_findings` | a backend ran and returned findings | `True` |
| `backend_reported_no_findings` | a backend ran and returned none. This is the backend's statement under its own criteria, recorded as such | `True` |

There is deliberately no value meaning "fine", "clear" or "approved", and the
two values that mean a backend answered name the backend as the author of the
answer.

### The three obligations on an implementation

1. **Never return a no-findings outcome for a design it did not examine.** If
   the service could not be reached, raise `ScreeningBackendUnreachable`. Any
   other failure may be raised as any exception.
2. **`backend_id` and `backend_version` must identify the service and its
   version** precisely enough that an entry stored today can be interpreted in
   a year. They go into every audit entry verbatim.
3. **`detail` must not overstate.** It is a sentence a person reads in an audit
   log. Section 16 governs it.

Obligation 1 is enforced rather than trusted. Backends are never called
directly; `run_screening_backend(backend, subject)` wraps every call and
converts each of these into a not screened outcome carrying the reason:

* raises `ScreeningBackendUnreachable` to `backend_unreachable_not_screened`
* raises anything else to `backend_error_not_screened`, with the exception type
  and message in `detail`
* returns something that is not a `ScreeningResult` to `backend_error_not_screened`
* returns `backend_reported_no_findings` together with a non-empty `findings`
  list, a self contradiction, to `backend_error_not_screened`, with the findings
  carried through unchanged
* returns `no_external_screening_ran` while not being the placeholder, to
  `backend_error_not_screened`

No path through `run_screening_backend` can produce a no-findings outcome for a
design the backend did not actually answer about.

### Wiring a real backend

```python
from packages.application.exports import export_screened_design
from packages.application.screening import ScreeningPolicy

export_screened_design(
    subject,
    format="genbank",
    payloads={"genbank": rendered},
    backend=MyBackend(),                 # omit for the no-op default
    policy=ScreeningPolicy(              # both default to True
        block_on_backend_findings=True,
        block_when_configured_backend_fails=True,
    ),
    audit_log=JsonlExportAuditLog(),
    validation_overall=report.overall,
)
```

`ScreeningPolicy` has exactly two fields, and that is asserted by a test. There
is no flag for the provenance assertion or the composition assertion: section
11.1 item 1 blocks an unattributable design from export without qualification,
and a gate with an off switch is not a gate.

### The default backend

`NoExternalScreeningBackend`, `backend_id = "no_external_screening_backend_configured"`,
version `"1"`. Open question Q8 records that no screening backend is available
to wire in this build, so this is what runs. It performs no I/O, submits
nothing (`sequences_submitted=0`, `bases_submitted=0`), and returns
`no_external_screening_ran` with this `detail`, verbatim:

> No external sequence screening backend is configured in this deployment, so
> no external screening examined this design. This entry records the absence of
> screening and must not be read as a screening result. The provenance
> assertion and the composition assertion in this same entry did run, and they
> are what this export was gated on.

It is deterministic: the same design gives a byte identical result every time.

### Recording the result in the design's provenance

Section 11.1 item 3 requires the result to be recorded in the design's
provenance. `ScreeningRecord.record_in_design(result: DesignResult)` returns a
copy with these entries appended, de-duplicated so recording twice is harmless:

```
provenance_assertion:attributed
composition_assertion:satisfied
rule_applied:<each distinct rule any rule derived span cited>
screening:no_external_screening_backend_configured:no_external_screening_ran
screening_note:no external sequence screening backend examined this design
```

The last line is appended whenever `external_screening_ran` is false, so a
reader skimming a provenance list cannot miss the absence of screening.

## 3. THE PROVENANCE ASSERTION: WHAT IT CHECKS AND WHAT IT BLOCKS

`packages/application/screening/provenance.py`, `assert_provenance(subject)`.

### The structure it runs on, and why it was needed

`DesignResult.provenance` is a list of source tokens. It records which sources a
design drew on. It cannot say which base came from which source, so on its own
it cannot support the base level claim section 11.1 item 1 makes.
`attribution.py` adds the missing structure: each exported sequence plus a list
of half open spans, each naming its `origin` and its `source` token.

`SequenceOrigin` has exactly four members and no fifth:

| Origin | Source |
|---|---|
| `registry_part` | section 11.1 item 1: a curated record in `data/parts` |
| `retrieved_template` | section 11.1 item 1: a record retrieved from the corpus |
| `user_input` | section 11.1 item 1: a sequence the user supplied |
| `published_rule` | section 4.2, which states the same property with "a published rule" as its third category. Covers an Appendix D recognition site, a published cloning vector overhang, and a spacer nucleotide whose identity is set by a documented deterministic rule |

A `published_rule` span must carry a non-empty `rule`, enforced by the model. A
`registry_part` span must carry a `part_id`, also enforced. So no span can
assert that it is attributed without naming where its bases came from.

### The six checks

Every failure is collected rather than the first one raised, so a blocked
export can be fixed in one pass. Each finding carries the sequence name, the
coordinates, and for a gap the actual bases.

1. **The subject carries at least one sequence.** None means there is nothing
   to attribute, so there is no evidence of attribution: verdict `UNKNOWN`.
2. **Every span lies inside its sequence.** A span that leaves it attributes
   nothing, so it is dropped and the bases it claimed become a gap.
3. **No two spans of one sequence overlap.** Two sources for one base is a
   contradiction, not an attribution.
4. **The spans cover the sequence completely.** Every uncovered span is
   reported with its coordinates and its bases. This is the unattributable
   sequence section 11.1 blocks on.
5. **Every span naming a sequence record has that source in the design's
   `declared_provenance`.** This closes the case where the provenance list a
   user reads and the bases in the file disagree. A `published_rule` span is
   exempt from this one check and only this one, because a capability's
   provenance list records the sources it drew sequence from and does not
   enumerate the rules its composer applied base by base; its rule is carried
   on the span, listed in `rules_applied`, and written into the design's
   provenance by `record_in_design`, so it still reaches the list a user reads.
6. **Every `registry_part` span resolves in `data/parts` and reproduces that
   record base for base**, forward or reverse complement. The reverse
   complement is allowed explicitly because a correct 3' ITR is the reverse
   complement of its own registry record. A span that claims a curated part and
   carries different bases is a modified element, which is a novel element.

### The verdicts, and which one permits an export

| Verdict | When | Export |
|---|---|---|
| `attributed` | every check passes | **permitted** |
| `unattributed` | any finding | **BLOCKED** |
| `unknown` | no sequence to attribute, or the registry could not be loaded while registry claims exist | **BLOCKED** |

`UNKNOWN` blocks. Section 3.3 constraint 4: a check that could not be evaluated
is never a pass. `ProvenanceAssertion.permits_export` is true only for
`attributed`, and there is no configuration that changes that.

### Proof from a test that an unattributable base blocks

`tests/screening/test_gate.py::test_an_unattributable_base_blocks_the_export`.
The fixture `subject_with_unattributed_base` splices ten bases into an
otherwise fully attributed cassette and shifts the downstream spans, so those
ten bases are covered by no span:

```python
def test_an_unattributable_base_blocks_the_export() -> None:
    log = InMemoryExportAuditLog()
    with pytest.raises(ExportBlocked) as raised:
        _export(subject_with_unattributed_base(), audit_log=log)
    blocked = raised.value
    assert blocked.record.allowed is False
    assert blocked.record.provenance.verdict is AssertionVerdict.UNATTRIBUTED
    assert "section 11.1 item 1" in " ".join(blocked.record.blocked_reasons)
    assert any(
        "GGGGGGGGGG" in (finding.bases or "")
        for finding in blocked.record.provenance.findings
    )
    # A blocked export is still recorded. Section 11.1 item 4.
    assert len(log.entries()) == 1
    assert log.entries()[0].decision == DECISION_BLOCKED
    assert log.entries()[0].blocked_reasons
```

`ExportBlocked` is raised, so no payload is returned: `test_a_blocked_export_releases_no_payload`
asserts that separately. The message the gate produces for the gap is:

```
10 bp of 'cassette' at (20, 30) trace to no registry part, no retrieved
template, no user supplied input and no named rule: GGGGGGGGGG. Section 11.1
blocks this design from export. Attribute the span or remove it from the design.
```

Two more tests prove the gate cannot be configured around it:

* `test_no_policy_flag_can_let_an_unattributable_design_through` asserts
  `ScreeningPolicy.model_fields` is exactly the two backend flags, then sets
  both to False and still gets `ExportBlocked`.
* `test_a_subject_with_no_sequence_blocks` asserts the `UNKNOWN` verdict blocks.

And on a real design rather than a fixture:
`tests/screening/test_export_hook.py::test_a_cassette_with_an_unattributable_element_is_blocked_by_the_hook`
takes a composed AAV cassette from `AAVDesigner`, clears the `source` on its
coding sequence element, and gets `ExportBlocked` plus a `blocked` audit entry.

### The registry-only composition assertion (section 11.1 item 2)

`composition.py`, `assert_registry_only_composition(subject)`. Verdicts
`satisfied`, `violated`, `unknown`; only `satisfied` permits an export.

It is deliberately narrow, because a wide version would be unprovable. It does
**not** claim to recognise a functional element in arbitrary DNA. It checks
that each of the four ways a span can be attributed holds up: a registry span
resolves and reproduces its record, a rule derived span names its rule, a user
input or template span names the input or record it came from. The violations it
reports are a part id outside `data/parts`, a registry span whose bases are not
that record in either orientation, and a rule derived span with no rule. It
also lists what the design was composed of: `registry_parts_used`, `rules_used`,
`user_inputs_used`, `templates_used`, and one `CompositionElement` row per span.

## 4. WHAT THE AUDIT LOG RECORDS

`packages/application/screening/audit.py`. One entry per call of the gate,
**permitted or blocked**. A blocked export is the entry most worth having, so
there is no path through the gate that writes nothing, and the entry is written
before the decision is reported.

The four fields section 11.1 item 4 requires, and where each lives:

| Required | Field(s) |
|---|---|
| what was exported | `capability`, `design_id`, `export_format`, `artifacts` (one row per artifact: `name`, `bytes_written`, `sha256`), `sequences` (one row per exported sequence: `name`, `length_bp`, `sha256`) |
| when | `recorded_at`, UTC, from an injected clock so an entry is reproducible in a test |
| the validator version | `validator_version`, with `validation_overall` beside it |
| the screening result | `screening`, the whole `ScreeningResult`, plus `external_screening_ran` as a plain boolean so nobody has to interpret an outcome string |

Also recorded: `decision` (`exported` or `blocked`), `blocked_reasons`,
`provenance_assertion` and `composition_assertion` in full (those are what the
export was actually gated on), `declared_provenance`, `adapter`, and
`schema_version` so a stored log stays interpretable across changes.

The SHA-256 digests are what make the entry evidential. They tie the entry to
the exact bases that left the system without the log having to store the
sequence. The digest is taken over the payload as it arrived, and the payload
released by the gate is byte identical to it, which
`test_the_hook_releases_the_payload_byte_for_byte` asserts.

### Sinks

* `InMemoryExportAuditLog`: the synchronous local path and the tests.
* `JsonlExportAuditLog`: append only JSON Lines on disk, one object per line,
  keys sorted so a diff is readable. The file and its parent directory are
  created on first write. Default path
  `data/audit/export_audit.jsonl`, overridden by the
  `CONSTRUCT_EXPORT_AUDIT_LOG` environment variable (section 3.3 constraint 2:
  configurable, with a documented default). `data/*` is gitignored, so the log
  is never committed, which is correct for an audit record.

## 5. THE EXPORT HOOK

`packages/application/exports.py`, one added function:

```python
export_screened_design(
    subject, *, format, payloads,
    validation_overall=None, backend=None, policy=None,
    parts=None, audit_log=None, now=utc_now,
) -> ScreenedExport
```

It validates `format` against the existing `SUPPORTED_EXPORT_FORMATS`, so a
recorded entry always names a format this build can write, and delegates to
`screening.screen_and_export`. It renders nothing: the AAV cassette is linear
and the plasmid path is circular, so each capability keeps its own codec and
this hook gates them all identically. It raises `ExportBlocked` when the gate
refuses, with the written audit entry attached to the exception.

The only other change to that file is a docstring on
`export_annotated_sequence` stating what it is, the plasmid codec, and what it
is not, the gate, with the reason: `AnnotatedSequence` has a sequence, a
topology and features, and nothing that says which base came from which source.
No existing codec, no existing behaviour and no existing test in
`tests/application/test_exports.py` was changed.

`ScreenedExport` is a frozen dataclass rather than a pydantic model, because
`SchemaModel` sets `str_strip_whitespace=True` and would trim the trailing
newline off a GenBank payload whose SHA-256 is already in the audit entry. The
bytes released are the bytes audited.

## 6. WHICH CAPABILITIES REACH THE GATE, AND THE ONE THAT CANNOT

An adapter in `packages/application/screening/adapters/` turns a capability's
own design object into an `ExportSubject`. Every adapter follows one rule, which
is what lets this package be a gate rather than a warning:

> An adapter emits a span only when the design proves where those bases came
> from. When it cannot, it emits nothing for that span. The uncovered span then
> blocks the export and is reported with its coordinates and its bases.

So an adapter never guesses, and a gap in an adapter surfaces as a blocked
export naming exact bases rather than as a silent pass.

| Capability | Adapter | What it attributes | Status |
|---|---|---|---|
| AAV | `adapters/aav.py` | the cassette, one span per `CassetteElement`, coordinates from `AAVDesign.layout()` | **fully attributed** on real composed cassettes |
| Assembly | `adapters/assembly.py` | one sequence per primer, which is the orderable DNA in the section 7.7 order table | **fully attributed** for gibson, golden_gate (BsaI, BbsI, SapI) and pcr_cloning |
| Guide RNA | `adapters/grna.py` | one sequence per spacer and one per cloning oligo | **fully attributed** for SpCas9, SaCas9 and LbCas12a, U6 plasmid and T7 in vitro |
| Plasmid | none | nothing. See below. | **cannot pass the gate** |

How each adapter proves rather than assumes:

* **AAV.** A `part_id` becomes a `registry_part` span that the assertion then
  verifies against `data/parts` base for base in either orientation. An element
  without a `part_id` is attributed from its `source`, which must declare
  itself as `user_input:<field>` or `retrieved_template:<id>`; anything else
  leaves the span uncovered. That is what catches a transgene resolver that
  returns an unprefixed token, and
  `test_an_aav_cassette_with_an_undeclared_source_blocks` is that case.
* **Assembly.** The binding region is compared against the named fragment at
  the recorded interval, forward for a forward primer and reverse complement for
  a reverse one. A Gibson tail is matched to one of the design's own
  `gibson_homology` junctions and verified to be a suffix of the upstream
  fragment. A Type IIS tail is split at the recognition sequence, which must
  occur exactly once, into the Appendix D site, the spacer and `top_cut_offset`
  filler bases, and any remaining bases, which must reproduce one of the
  design's own junction overhangs (attributed to the standard that defined it,
  or to the downstream fragment whose first bases it is).
* **Guide RNA.** A spacer is located on the user's own `target_sequence` at the
  recorded placement, so `test_a_guide_placed_off_its_own_target_blocks` shows a
  mis-placed guide blocking its own export. Overhangs and 3' additions are
  compared against the published record for the vector the plan names. The
  single G, and the matching C on the antisense oligo, that the published U6 and
  T7 protocols add when a spacer does not begin with G is a rule derived span of
  exactly one base; anything longer is not attributed. The constant T7 scaffold
  oligo, which carries no guide specific sequence, is compared against the
  recorded template for that nuclease.

### FINDING: the plasmid capability's provenance is not sufficient for its own export

This is reported rather than accommodated. The check was not loosened to let it
through.

`packages.application.designs.DesignRecord`, which is what
`GET /v1/designs/{design_id}/export` exports, holds `design_id`, `session_id`,
`job_id`, `annotated_sequence` and two timestamps. `AnnotatedSequence` holds a
sequence, a topology, features, a vector profile and a completeness flag. There
is no field anywhere on that path that says which base came from which source.

The information exists one layer up and is dropped.
`packages.generation.generator` produces
`GeneratedSequence(annotated_sequence=..., model_version=..., parent_template_ids=[template.id])`,
but `DesignStore.create` takes only the `annotated_sequence`, so
`parent_template_ids` never reaches the store and never reaches the export
route. Consequently:

* there is no plasmid adapter, and `subject_for_design` raises
  `NoAttributionAdapter` for anything it does not recognise rather than
  returning an empty subject, so a plasmid design cannot silently pass;
* if a plasmid subject were built with no spans, the provenance assertion would
  return `UNKNOWN` and block, which is the correct outcome for a design whose
  attribution cannot be evaluated;
* the plasmid export route therefore still calls `export_annotated_sequence`
  directly, the codec, and does not go through the gate. That is stated here
  rather than hidden, and the function's own docstring now says it is not the
  gate.

**Second part of the same finding, and the more serious half.**
`packages.generation.generator.CarbonGenerator` composes its candidate as
`splice_generated_segment(template_sequence, segment)` where `segment` is a
continuation sampled from a language model. Those bases trace to a model, not to
a curated part, a retrieved record, a user supplied input or a named rule. A
design produced that way has sequence that section 11.1 item 1 makes
unattributable and that section 11.1 item 2 describes as a novel element
synthesized de novo. If a Carbon generated plasmid were routed through this
gate, it would be blocked, correctly. It is not currently routed through it,
because of the gap above, and it is not on the demo path (`FakeGenerator` is,
per specification 1.3). This is an operator and WP-11 decision, not something
WP-08 should resolve unilaterally late in the build.

**What closing the gap takes.** Carry `parent_template_ids` from
`GeneratedSequence` through `DesignStore.create` to `DesignRecord`, record the
marker swap coordinates when `FakeGenerator.marker_swap` applies, write a
plasmid adapter that emits a `retrieved_template` span for the template derived
region and a span for each swap, and route the export endpoint through
`export_screened_design`. That touches `packages/application/designs.py`,
`packages/generation/generator.py` and `services/api/app.py`, none of which

## 10. SPEC CHALLENGES AND CROSS-WP REQUESTS

Both are also appended to `PROGRESS.md`.

**Spec challenge, the fourth origin.** Section 11.1 item 1 names three
categories: a registry part, a retrieved template, the user's own supplied
input. Section 4.2 states the same property with three categories of which one
differs: "the user's input, a curated part record, or a published rule". The
union is four, and the fourth is load bearing: an Appendix D Type IIS
recognition site in a primer tail, a published cloning vector overhang in a
guide oligo, and the single G the published U6 protocol prepends are none of
them a part record, a retrieved record or user input, yet each is exported and
each is fully traceable. `SequenceOrigin` therefore has four members. A
`published_rule` span must name its rule, every distinct rule is listed in the
audit entry, and the gate writes each rule into the design's provenance, so
rule derived bases are enumerated rather than absorbed into a general pass.

**Spec challenge, the spacer nucleotide rule.** Appendix D fixes how many
nucleotides sit between a Type IIS recognition site and the cut. It does not fix
their identity, and `packages/generation/assembly/designer.py::_filler` sets it
by a documented deterministic A, C, G, T scan that takes the first base adding
no new copy of the site. Those bases are attributed as `published_rule` citing
that rule by file and function name, not as a part or a template. The rule text
is in `adapters/assembly.py::SPACER_RULE` and appears verbatim in the audit
entry and in the design's provenance for any assembly that uses it.

**Cross-WP request to the owner of `packages/application/designs.py`,
`packages/generation/generator.py` and `services/api/app.py`.** Section 6 of
this file. The plasmid export path cannot pass the section 11.1 gate because
`parent_template_ids` is produced by the generator and dropped before the
design store, so no base in an exported plasmid can be attributed. Closing it
needs those three files, which WP-08 does not own.

**Cross-WP request to WP-11 and the operator.** `CarbonGenerator` splices a
model sampled continuation into a template. Those bases are unattributable
under section 11.1 item 1 and are a de novo element under item 2. It is not on
the demo path, `FakeGenerator` is. If it is ever enabled, the gate would block
its output, correctly, and the section 16 claim about curated composition would
need qualifying for that generator.

**Cross-WP request to WP-07.** The screening result is already in the design's
provenance after `ScreeningRecord.record_in_design`, as
`screening:<backend id>:<outcome>` plus, when nothing was screened, a
`screening_note:` line in plain words. If the UI shows a provenance or
screening panel, render the `screening_note:` line and never render an absence
of findings as a result. `external_screening_ran` on the audit entry is the
boolean to drive that off.
