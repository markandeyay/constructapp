# WP-09: Test harness extension

Owner: wp09-harness. Files: `tests/gold/runner.py`, `tests/gold/test_gold_runner.py`,
`tests/gold/__init__.py`, the `eval-*` Makefile targets.

## Make targets

| Target | What it does | Needs DB |
| --- | --- | --- |
| `eval-capabilities` (new) | Runs `python -m tests.gold.runner` over `tests/gold/<capability>/`. Writes `data/eval/capabilities/capability_gold.json` (no timestamp, byte-reproducible). Exit 1 on any disagreement. | No |
| `eval-plasmid` (new, extracted) | The old `eval-all` body unchanged: `eval-retrieval`, `eval-generation`, `validate-sample MODE=gold`, `quality-report`, dashboard. Nothing dropped. | Yes (corpus) |
| `eval-all` (changed) | Runs BOTH halves every time (`eval-capabilities`, then `eval-plasmid`), prints a two-line summary, exits non-zero if either failed. | Partly |
| `eval-check` (changed) | Same two halves, then the `continuous check` regression thresholds only when `eval-plasmid` succeeded. Prints a summary naming which half failed. Exit 0 only if all three are clean. | Partly |

Variables: `CAPABILITY_GOLD` (default `tests/gold`), `CAPABILITY_GOLD_OUT`
(default `data/eval/capabilities`), `CAPABILITY_GOLD_REQUIRE=1` (zero cases becomes an error;
WP-06 or WP-11 should switch this on once the gold sets exist).

All recursive invocations keep the `"$(MAKE)"` quoting required by GNU Make 3.81 here.

## Why this decomposition

`make` stops at the first failing prerequisite line, so with the old chain a failed
`eval-retrieval` (empty corpus: `relation "plasmids" does not exist`) hid whether anything
after it passed. The capability validators are pure functions over sequences, so their gold
evaluation is split into its own target with no database dependency. `eval-all` and
`eval-check` run both halves unconditionally and report each verdict separately, so a corpus
failure can never mask the capability result, and the capability result can never mask the
corpus failure.

## Corpus problem

`eval-retrieval` is NOT skipped, softened or caught. It still runs inside `eval-plasmid`, still
fails with the same Postgres error, and `eval-all` / `eval-check` still exit non-zero while the
corpus is empty. What changed is that the failure is now labelled ("plasmid pipeline (needs
corpus): FAIL, regression check NOT run") next to an independent capability verdict. The
regression-threshold step is not run against a missing dashboard, and the summary says so.
The corpus needs operator authorization to repopulate; nothing here works around it.

## Case file schema (hand this to WP-06)

Files: `tests/gold/<aav|assembly|grna>/**/*.json`. One case object, or a JSON list of them.
Discovered in sorted path order. `case_id` must be unique per capability. `capability` must be the
directory name or the CapabilityKind value (`grna` dir may say `grna` or `guide_rna`). `input` is
required: it is parsed into the capability's `design_model` (if the registry entry has one) and
passed to its `validator.validate`.

Known-bad (exactly one of `expect_check`/`tier` must be present):

```json
{
  "case_id": "aav.bad.over_hard_limit",
  "capability": "aav",
  "expect_overall": "fail",
  "expect_check": "aav.packaging_limit",
  "expect_severity": "fail",
  "rationale": "Cassette totals 5,340 bp, above the 5,200 bp hard ceiling.",
  "must_also_report": ["remediation_suggestion"],
  "allowed_extra_fail": [],
  "input": {}
}
```

Correct only if ALL hold: overall equals `expect_overall`; the check named `expect_check` is
present and reports `expect_severity` (UNKNOWN or absent never matches); NO other check reports
FAIL (unless listed in `allowed_extra_fail`, an explicit, reported escape hatch for genuine
cascades, use sparingly); every `must_also_report` entry is satisfied. A string entry is satisfied
by a non-UNKNOWN check with that id, or a non-empty attribute/key of that name on any check or on
the report. An object entry `{"check": id, "severity": s}` requires that check at that severity.
Unverifiable requirements fail, never pass.

Known-good Tier A: `{"case_id", "capability", "tier": "A", "input"}`. Must be overall pass with no
WARN, FAIL or UNKNOWN.

Known-good Tier B: adds `"expected_warnings": [{"check": id, "justification": text}, ...]`
(non-empty). No FAIL, and the set of WARN checks must equal the documented set exactly (documented
warnings present is the expected outcome; a missing or extra warning is a disagreement).

Optional on any case: `expected_unknown: [check ids]` to permit named UNKNOWN checks.

Other rules enforced: the runner recomputes overall as the worst non-UNKNOWN severity and flags a
validator whose declared overall disagrees; a validator exception, unreadable file, malformed case,
duplicate id, or unresolvable validator is a disagreement (UNEVALUABLE), never a pass.

## Reporting

Per capability: counts and accuracy for all, known-good, tier A, tier B, known-bad, malformed count,
UNKNOWN report count; then every disagreement with case id, source file, expected, actual, and each
specific problem. Zero cases prints "0 cases found. This capability is NOT covered by any gold set
yet." and accuracy n/a, exit 0 (exit 1 with `--require-cases`).

## How the wrong-reason catch is proven

`tests/gold/test_gold_runner.py` (30 tests). Key ones:
`test_bad_case_failing_for_the_wrong_check_is_a_disagreement` (overall FAIL matches, but the named
check passed and a different check failed: reported, with both the named-check and unexpected-FAIL
problems), `test_accidentally_right_extra_fail_is_caught_even_when_named_check_fails`,
`test_tier_a_with_a_warning_is_a_disagreement`, `test_unknown_on_named_check_is_never_a_match`,
`test_end_to_end_disagreement_listed_and_exit_nonzero`, `test_zero_cases_reports_zero_and_exits_zero`.

## Dependency on WP-02

The runner resolves validators through `CAPABILITY_REGISTRY` (tries
`packages.core.capability_registry`, then `packages.core.schemas.registry`, then
`packages.core.registry`). Each spec should expose `validator` (or `validator_factory()`) and
optionally `design_model`. Cross-WP request appended to PROGRESS.md. Until then, any real case
reports UNEVALUABLE and fails loudly. Note `CheckResult` in section 5.1 has no field for
remediation text; `remediation_suggestion` in `must_also_report` therefore needs to be a check id
or a field that WP-03 exposes. WP-03 and WP-06 should agree on this.

Note on the grep gate: `apps/web/.next/` (git-ignored build cache, not authored here) contains the
historical working directory name in embedded source-map paths. Everything else is zero hits.
