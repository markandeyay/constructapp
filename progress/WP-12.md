# WP-12: the plasmid capability joins the multi-capability gold runner

Branch `feat/plasmid-adapter`. The plasmid gold set was measured by the older
harness (`packages/validation/eval.py`), which checks an aggregate verdict and
the expected failing checks, but never asserts that no OTHER check also failed.
Section 9.3 names that third assertion as the one that catches a validator which
is accidentally right. AAV, assembly and guide RNA were subject to all three
assertions. Plasmid was not. It is now.

No threshold, constant or biological rule was changed. No verdict was changed.
`packages/validation/engine.py` was not touched.

## What was added

* `packages/core/schemas/plasmid.py`: `PlasmidDesign`, the single design object
  the section 5.3 interface passes. It carries the two inputs the engine already
  takes (`design_spec`, `annotated_sequence`) plus optional `design_id` and
  `provenance`, so a gold case input is a curated record's two blocks unchanged.
* `packages/validation/plasmid/`: the adapter. `constants.py` holds the check id
  mapping, the labels, the severity mapping and the threshold mirror.
  `validator.py` holds `PlasmidValidator` and `build_validator`.
* `packages/core/capability_registry.py`: `PLASMID_SPEC` now carries
  `validator_ref` and `design_model_ref`, so the runner resolves plasmid exactly
  as it resolves the other three. The three delimited WP regions were not
  touched.
* `tests/gold/runner.py`: `plasmid` added to `EXPECTED_CAPABILITIES`, so losing
  `tests/gold/plasmid/` reports a capability with zero cases instead of quietly
  reporting three.
* `scripts/convert_plasmid_gold.py` and `tests/gold/plasmid/`: the conversion and
  its 88 cases.
* `tests/validation/test_plasmid_adapter.py` (17 tests) and
  `tests/gold/test_plasmid_gold_cases.py` (6 tests).

## The check id mapping

The engine's own `ValidationCheck.name` values are already the ids the curated
data uses, so the mapping is the identity. It is written out in full in
`CHECK_ID_BY_ENGINE_NAME` anyway, so a future rename has one place to record
itself and the 52 known-bad expectations transfer with no translation.

| Engine `ValidationCheck.name` | Contract `CheckResult.check_id` | Label | Known-bad cases |
| --- | --- | --- | ---: |
| `restriction_site_conflicts` | `restriction_site_conflicts` | Restriction site conflicts | 13 |
| `repeat_and_instability` | `repeat_and_instability` | Repeats and synthesis instability | 13 |
| `codon_usage` | `codon_usage` | Codon usage for the requested host | 13 |
| `regulatory_compatibility` | `regulatory_compatibility` | Regulatory element compatibility | 13 |

Severity mapping (`SEVERITY_BY_ENGINE_STATUS`), total and lossless, so no
verdict can move: `PASS` to `pass`, `WARN` to `warn`, `FAIL` to `fail`. The
engine has no UNKNOWN status, so nothing maps to UNKNOWN from a real run.

`validator_version` is `plasmid-adapter-1.0.0+phase3-validation-v1`. The engine
owns every plasmid threshold and versions them with `CHECK_VERSION`, so
embedding that string makes section 5.4 rule 4 hold without anyone having to
remember to edit the adapter when a threshold changes.

## Where the engine cannot express what the contract wants

Section 3.3 constraint 4: say so, do not invent.

* `observed`, `threshold` and `tier` are `None` on every check. The engine
  reports prose, not a measured quantity against a named bound, and the contract
  makes these optional precisely so an adapter need not fabricate them. The
  thresholds that were applied are reported through `parameters_used`, which is
  what rule 3 actually asks for.
* `remediation` is `None`. The engine's messages already carry the actionable
  instruction inline (rule 2). There is no structured fix list to surface, and
  writing one would be new content published under the engine's name.
* `ValidationCheck.failure_context`, which the engine sets on some regulatory
  failures, has no field in `CheckResult`, and `CheckResult` forbids extra
  fields. It is therefore not in the report. It is not lost either: it is read
  through `PlasmidValidator.failure_contexts`.
* UNKNOWN is produced in exactly two situations, neither of which a real engine
  run reaches: a check emitted under a name the adapter has no mapping for, and a
  mapped check the engine did not emit at all. Both carry the reason in the
  message. UNKNOWN never improves a verdict, so neither can read as a pass.

`parameters_used` reads live from the engine wherever the engine exposes the
value it applied (`repeat_profile_for`, `restriction_context_from_spec`,
`host_context`, `HOST_CODON_WEIGHTS`, the regulatory token sets), so those
numbers cannot drift from one copy to another. Four thresholds are written
inline in the body of a check and have no accessor, so they are mirrored in
`MIRRORED_THRESHOLDS` with the exact source expression each one mirrors: the MCS
padding of 6 bp, the 100 bp GC window with its 0.20 and 0.80 bounds, and the
codon adaptation bounds 0.55 and 0.75.
`test_mirrored_thresholds_still_exist_in_the_engine_source` reads the engine's
source and fails if any of those expressions is gone, so an engine threshold
edit cannot leave the mirror quietly wrong.

`provenance` is never empty (rule 5). A design that declares its own keeps it;
otherwise the sequence was handed to the validator rather than composed from
registry parts, and that is what is recorded: `user_input:annotated_sequence`,
plus `design_spec:source=<source>` when the spec declares one.
`PlasmidValidator.design_result` builds a contract `DesignResult`, which is what
proves rules 3 and 5 hold: the model rejects an empty `parameters_used` and an
empty `provenance`, so that method cannot return without both.

## How the adapter was proved to change no verdict

`tests/validation/test_plasmid_adapter.py::test_adapter_changes_no_verdict_on_any_curated_record`
drives the raw `ConstraintEngine` and the adapter over every curated record, all
88 of them (36 known-good, 52 known-bad), and asserts for each one:

* the adapted check ids are the engine's check names mapped in order, so the
  check set and its order are identical;
* each check's severity is exactly `SEVERITY_BY_ENGINE_STATUS[engine status]`;
* each check's message is the engine's message, string equal;
* each check's coordinates are the engine's region start and end, or `None` when
  the engine reported no region;
* the adapted `overall` equals the engine's `overall` lowercased, and equals what
  the shared helper `overall_from_checks` recomputes from the adapted checks;
* no check is UNKNOWN.

That is 88 records times 4 checks, so 352 per-check verdict comparisons plus 88
overall comparisons, all equal. A second test
(`test_every_curated_overall_distribution_is_preserved`) compares the whole-set
distribution of overall verdicts between engine and adapter as a count, so a
uniform shift could not hide behind per-case equality. The counts match and sum
to 88.

Independent of the adapter, the old harness still reports the same numbers:
`make validate-sample MODE=gold` gives accuracy 1.000 and
`phase3_gate_met: true` on 36 known-good and 52 known-bad, and `make eval-check`
passes all three of its summary lines.

## The conversion script

`scripts/convert_plasmid_gold.py`, run from the repository root. It reads
`data/eval/validation/curated_known_good.jsonl` and
`curated_known_bad.jsonl` and writes `tests/gold/plasmid/tier_a.json`,
`tier_b.json` and `known_bad.json`. The two source files are not modified.

It invents no expectation. Every `expect_check` comes from the record's
`expected_failing_checks`, every tier from the record's `tier`, every
justification from the record's own prose, and each case `input` is the record's
`design_spec` and `annotated_sequence` verbatim. What the script adds is the
runner's field names, a case id, and the fields that keep a case traceable:
`defect_type`, `check_category`, `rationale_citation`,
`construction_procedure`, `source_plasmid_id`, `source_case_id` and
`source_record_path` on a known-bad case; `name`, `accession`,
`vector_profile`, `tier_label`, `known_good_basis`,
`citation_source_evidence` and `feature_evidence` on a known-good one. Every
case also records `converted_from`, the source file it came from.

Case ids: `plasmid.bad.<source case id without the ckb_ prefix>`, for example
`plasmid.bad.restriction_000`; `plasmid.good.a.<slug of plasmid_id>` and
`plasmid.good.b.<slug of plasmid_id>`, for example
`plasmid.good.a.curated_puc19`. They are derived from the source identifier
rather than numbered, so adding a record never renumbers an existing case.

A known-bad `rationale` is the record's own rationale, then the injected defect
and its category, then the sentence that names the check the case asserts and
why section 9.3 wants it named, then a note that the construct is the named
known-good source record with only that defect applied. A Tier B justification
joins the two pieces of prose the source carries for each warning (the short
`rationale` on the `expected_warnings` entry and the longer
`warn_justifications` entry), because dropping either would lose a reason a
reviewer wrote down.

The script refuses rather than guesses. It raises on a known-bad record whose
`expected_failing_checks` does not have exactly one entry, on an entry naming a
check the adapter does not report, on a tier that is not A or B, on a Tier A
record that declares warnings, on a Tier B record with no warning or a warning
at a status other than WARN, on a warning with no justification, and on a
duplicate case id. Running it twice writes byte-identical files, and
`tests/gold/test_plasmid_gold_cases.py::test_committed_cases_match_a_fresh_conversion`
regenerates into a temporary directory and compares, so the committed cases
cannot drift from the script that produced them.

## Cases that did not pass

None. All 88 converted cleanly and all 88 agree, including under the two
assertions the old harness never made: every known-bad case is caught by the
check it names, and no known-bad case produces a FAIL on any other check. This
was checked against the engine before any case file was written, so the
conversion was not an attempt that then needed adjusting; nothing was edited to
make a case green and nothing in the adapter was loosened.

The result is worth stating precisely, because it is a stronger claim than the
old harness could make. Previously the plasmid set was known to produce a FAIL
verdict with the expected check among the failures. It is now known that each of
the 52 known-bad cases fails on exactly the one check it names and on no other,
that each of the 25 Tier A cases validates with no WARN, no FAIL and no UNKNOWN,
and that each of the 11 Tier B cases warns on exactly its documented set.
