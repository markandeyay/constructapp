# WP-14: screening gate wired into the remaining capabilities

Model: Opus. Follows WP-13, which wired the section 11.1 gate into the AAV routes
and recorded why the other three were not yet covered.

## Result in one line

Assembly and guide RNA are now gated. Plasmid is not, and the reason is
architectural rather than remaining effort; it is set out in full below, with the
decision it needs left open rather than taken unilaterally.

## The blocker WP-13 named, and how it was removed

WP-13 recorded that assembly and guide RNA could not be gated because
`SUPPORTED_EXPORT_FORMATS` was `{genbank, fasta}` and those capabilities export
tables. The fix was not to widen that set, which would have introduced a silent
bug: `read_annotated_sequence` falls through to the FASTA parser for any format
that is not GenBank, so admitting "tsv" there would have made a TSV order table
parse as FASTA instead of failing.

So the two vocabularies are now separate constants in
`packages/application/exports.py`, with the trap written down next to them:

* `SUPPORTED_EXPORT_FORMATS` stays `{genbank, fasta}`. It guards the codecs, and
  `validate_export_format` still rejects a table format.
* `TABLE_EXPORT_FORMATS` is `{csv, tsv}`.
* `AUDITABLE_EXPORT_FORMATS` is the union. It guards the audit entry through the
  new `validate_auditable_export_format`, which is what `export_screened_design`
  now calls, so a blocked guide RNA export can record that it was a TSV.

Verified both directions: `validate_auditable_export_format("tsv")` returns
`"tsv"`, and `validate_export_format("tsv")` still raises
`unsupported export format 'tsv'; expected one of: fasta, genbank`.

## What each route now does

| Route | Screened payload | Format recorded | Refusal |
|---|---|---|---|
| `POST /v1/assembly/design` | the order table CSV | `csv` | 200, table withheld in both renderings |
| `POST /v1/assembly/order-table.csv` | the same table | `csv` | 409 with code `export_blocked` |
| `POST /v1/grna/design` | both TSV tables | `tsv` | 200, both tables withheld |

The 409 on the CSV endpoint is the one deviation from the WP-13 pattern, and it is
deliberate. That endpoint exists only to hand over the table. There is no report
in its response to read instead, so a 200 with an empty body would be a worse
answer than a refusal a caller cannot miss. The error carries the code
`export_blocked` and the gate's own text, which was checked: the app's
`HTTPException` handler passes a dict detail through intact rather than replacing
it with a generic friendly message.

## A contract change, made explicitly rather than by quietly loosening

`AssemblyOutputs.order_table` and `order_table_csv` required at least one row.
That constraint encoded an assumption that stopped being true when the gate
arrived: a composed assembly always has primers, but an assembly whose primers
cannot all be attributed has an order table that must not be handed over. Both
fields now default to empty, and empty means withheld.

The schema docstring says so, and says that a caller must read
`AssemblyResponse.export_blocked` rather than infer from a non-empty table that an
export was permitted. Nothing substitutes a placeholder row: section 4.3 forbids a
placeholder sequence precisely because it gets exported as orderable DNA. No test
depended on the old constraint, which was checked before changing it.

## What is withheld, and what deliberately is not

The design, the validation report, the protocol, the junction map and the ranked
guides all survive a block. Section 11.1 blocks the export and not the design, and
the researcher needs the report to act on the reason. Only the rendered export
artifacts are withheld. This matches the AAV precedent from WP-13, where the
blocked response keeps its 14 checks.

## Web surface

The UI consumed `outputs.order_table_csv` and `exports` directly. An existing
`.filter((file) => file.content)` meant a blocked design could not produce an
empty download, which was luck rather than design, but the buttons would simply
have vanished with nothing said. `exportBlockReasonFor` now feeds the gate's
reason into the existing `disabledReason` slot, so a refusal is visible instead of
silent. Types gained optional `export_blocked` and `export_block_reason` on all
three capability responses. Typecheck, lint and build all pass.

## Plasmid: why it is not gated

`GET /v1/designs/{design_id}/export` calls the codec directly. Gating it needs an
`ExportSubject`, which needs spans, and the plasmid path records none.

* `DesignRecord` carries `design_id`, `session_id`, `job_id`,
  `annotated_sequence` and two timestamps. No template identity.
* `AnnotatedSequence` carries a sequence, a topology, features, a vector profile
  and an annotation flag. `AnnotatedFeature` has coordinates but describes what a
  region is, not where its bases came from, and the features on a stored design
  come from re-parsing, so they are inferred annotations rather than provenance.
* `CapabilityKind.PLASMID` is absent from `ADAPTED_CAPABILITIES` and
  `subject_for_design` raises `NoAttributionAdapter` for anything it does not
  recognise. So a plasmid design cannot silently pass the gate. It never reaches
  it, which is the safe failure direction and is why this is a documented gap
  rather than a hole.

The template id does exist upstream, on `GeneratedSequence.parent_template_ids`,
and the corpus retains full sequences, so a genuinely verified attribution is
reachable. It is not reachable without threading: the id would have to survive
into the design record, and `assert_provenance` would need a corpus reader to
base-compare a retrieved template span at all.

**The limit of the existing assertion, stated because it bears on what may be
claimed.** `assert_provenance` base-compares only `REGISTRY_PART` segments,
against `data/parts`. A `RETRIEVED_TEMPLATE` or `USER_INPUT` segment is checked
only for being declared in the design's recorded provenance, not compared against
any source. For the three gated capabilities this is sound: their spans are either
registry parts, which are base-compared, or the user's own submitted bytes, where
there is nothing external to compare against. It does mean that a design which
declared a `retrieved_template:` source would have that span taken on trust, and
that is exactly the weakness a plasmid adapter must not be built on top of.

So the two honest options for plasmid are to refuse every plasmid export, or to
leave the path ungated and documented. The first is a material product change and
the second is the current state. This package took neither silently: it left the
state as it is, documented it in the README in those terms, and raised the choice.
What it did not do is emit a whole-sequence span attributed to a template nobody
verified, because that would make the audit log assert a verified attribution that
was never verified, which is worse than no entry at all.

### The suite no longer writes into the repository's audit log

Every design request on a gated route appends an entry, so the assembly and guide
RNA route tests began appending to the real `data/audit/export_audit.jsonl`, as
the AAV tests had. The per module fixture WP-13 added is replaced by one autouse
fixture in `tests/conftest.py` covering the whole suite, so a route test added
later inherits the redirect instead of quietly reintroducing the problem. It is
function scoped, not session scoped, so a test can assert exactly how many entries
its own request wrote. Verified: after a full suite run, `data/audit` does not
exist.

### The tests were checked for being vacuous

Two deliberate tampers, both reverted.

1. Gate neutered, so that it always allows: the 4 blocking tests across both files
   fail.
2. Audit log argument removed, reproducing exactly the item 4 defect WP-13 found
   and fixed: 7 tests fail.

The second matters most. That defect originally shipped past a byte identical demo
diff, because a gate that records nothing produces the same response as one that
records correctly. There is now a test that fails for it.

## Cost

Measured against the same build with the gate short circuited.

* Assembly: 15.5 ms against 17.3 ms median, which is inside the measurement noise.
* Guide RNA: 258.2 ms against 234.6 ms median, so roughly 23 ms on a 235 ms
  request. It screens 30 sequences, hashing each, which is where that goes.

Not optimised, because the number is small next to the work it guards and
optimising a correctness gate before it is proven correct is the wrong order.
