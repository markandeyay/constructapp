# WP-15: verified provenance for the plasmid export path

Model: Opus for the screening and route work, Opus for the generation and
persistence threading, which ran as a separate worker. Follows WP-14, which gated
three capabilities and left plasmid ungated with the blocker written down.

## What changed, in one line

The plasmid export path is now gated, and its attribution is verified against the
corpus record rather than asserted. Changing one base of a 4,245 bp candidate is
enough to be refused.

## Why this was not just more route wiring

WP-14 recorded two honest options for plasmid: leave it ungated, or refuse every
plasmid export. Both were true at the time, because nothing on that path recorded
where any base came from. `DesignRecord` held an `AnnotatedSequence` and nothing
else, and `AnnotatedFeature` has coordinates but says what a region is rather than
where it came from.

A third option existed and WP-14 named it without taking it: thread real
provenance. That is what this package does. The reason it is worth the work is
that the plasmid path is the one case in the build where a template span can be
*checked*. The corpus retains the complete sequence of every record it holds, so
there is something to compare against. The three capabilities wired earlier
compose from the registry plus the user's own input, and for those a template span
would have had nothing behind it.

What was deliberately not done, in either package: emit a span attributing the
whole candidate to a template nobody fetched. That would have made the audit log
state a verified attribution that was never verified, which is worse than no entry.

## The chain, end to end

1. **`SequenceSpan`** (`packages/core/schemas/models.py`). Carries the span's
   coordinates in the candidate AND its coordinates in the source record, plus the
   provenance token and the bare source id. Its invariant is that both ranges are
   the same length, enforced at construction, so a span claiming 300 bases of a
   template for 200 bases of output is rejected when it is built rather than
   puzzled over when it is checked.

2. **Generators** (`packages/generation/generator.py`) emit spans.
   `FakeGenerator`, which is what both production wirings use, copies the template
   verbatim and emits one span over the whole candidate. With a marker swap it
   emits two spans for the unchanged flanks and none for the replacement, so the
   swapped bases are uncovered and block. `CarbonGenerator` emits a span for the
   kept template prefix and none for the model sampled tail, so model written
   sequence cannot reach an export.

3. **Persistence** (`packages/application/designs.py`,
   `packages/application/design_jobs.py`). `DesignRecord` gained `template_ids`
   and `sequence_spans`; both stores round-trip them, Postgres through the
   previously unused `payload` column. A row written before this change loads with
   both fields empty rather than raising.

4. **The adapter** (`packages/application/screening/adapters/plasmid.py`) turns
   those spans into `RETRIEVED_TEMPLATE` segments carrying the template id and the
   source coordinates. `CapabilityKind.PLASMID` is now in `ADAPTED_CAPABILITIES`.

5. **The assertion** (`packages/application/screening/provenance.py`) gained a
   seventh check: a template span is compared against the record it names, at the
   coordinates it claims. This is the same standard check 6 already applied to a
   registry part, extended to a record the span covers only part of.

6. **The route** (`services/api/app.py`) screens before handing over the file, and
   `build_local_app` supplies a `template_reader` backed by the real corpus.

## Two design decisions worth defending

**The comparison is against the live corpus, not a copy stored with the design.**
Storing the template's bases next to the candidate would have made the lookup free
and the verification worthless: it would compare the design against a copy written
at the same moment by the same code. The reader goes to the corpus.

**`template_reader` is injected, and its absence refuses rather than permits.**
Reading the corpus needs the retrieval layer, which `services/api/app.py` does not
depend on. More importantly, a deployment with no reader cannot verify a template
claim, and an unverifiable claim is UNKNOWN, and UNKNOWN blocks. So a deployment
must supply the thing that makes verification possible in order to serve plasmid
exports at all. The alternative, serving them unscreened when the reader is
missing, is the silent default section 3.3 constraint 4 exists to forbid.

## A tightening this introduces, stated because it is a behaviour change

Before this package, a `RETRIEVED_TEMPLATE` span was checked only for having its
source token declared in the design's provenance. It was never compared against
anything. Now a template span without a template id or without source coordinates,
or whose record was not supplied, is UNKNOWN and blocks.

No test and no gold case relied on the looser behaviour, which was checked before
changing it: the only test touching `RETRIEVED_TEMPLATE` asserts that
`classify_source` returns the right enum. The capabilities wired earlier emit user
input spans, not template spans, so none of them is affected. But a future adapter
that emits a bare template token will now be refused instead of believed, and that
is the intended direction.

## One defect found by self check, in the delegated work

The worker emitted `CarbonGenerator` spans whose coordinate arithmetic was
`len(template) - len(segment)`. That is correct only because `_generate_segment`
returns an already normalized segment, so its length matches the length
`splice_generated_segment` works with internally. `normalize_dna` strips
whitespace, so had that normalization moved or been removed, the span would have
silently credited model written bases to a real corpus record.

The arithmetic was correct as written, and was verified as correct. The coupling
across two functions was not acceptable on that particular path, so the claim is
now checked against the candidate before it is made: a prefix that does not
reproduce the record yields no span, which blocks, rather than a confident wrong
one.

Recorded because the report said the coordinates were determinable exactly and
they were. The problem was not the value, it was what the value depended on.

## A latent fragility found, pre-existing, now fixed

`pytest tests/services` on its own failed to collect, on pristine master as well,
which was confirmed by stashing. `services/api/app.py` imported
`services.api.routes` at module scope, and `services/api/__init__.py` imports
`app` back. That cycle is harmless under a normal import but breaks when the test
shim in `tests/services/api/__init__.py` executes the file directly. The full
suite passed only because an alphabetically earlier test imported the module
normally first.

The routes import is now deferred to call time inside `create_app`. `pytest
tests/services` passes standalone, and so does every subset tried.

## Also fixed: a message that named a detail it withheld

The provenance assertion's summary ends with "every problem is listed in findings
with its coordinates", and nothing ever put those findings in front of an API
caller. A researcher told that 3,075 bp of 3,802 bp are unattributable still had to
be told which 3,075. `block_findings` now travels with the refusal, in the error's
`details`, for the plasmid and assembly file endpoints.

### Against real corpus data, not fixtures

* A real 4,245 bp corpus record, `curated:pACYC184`, through the real generator,
  stored, exported: **200**, 5,776 bytes of GenBank, verified against the live
  corpus record.
* The same design with **one base changed at position 2000**: **409**, code
  `export_blocked`, finding reads "claims bases (0, 4245) of template
  'curated:pACYC184' but differs from that record in 1 of 4,245 positions".
* Both outcomes appear in the audit log, one `exported` and one `blocked`.
* Postgres round-trip of `template_ids` and `sequence_spans` through the `payload`
  column, against the running database: both survive and compare equal to the
  originals. A legacy row with `payload = '{}'` loads with both fields empty.
  A NULL payload is unreachable, because the column is NOT NULL, so the worker's
  handling of that case is defensive and untriggerable rather than wrong.
* Generator spans were checked by comparing each span's candidate bases against
  its claimed template bases rather than by trusting the reported coordinates. All
  spans reproduce the template, and for the marker swap case the uncovered
  positions are exactly the swapped-in bases.
* Corpus unchanged at **4,455** records; test rows written during verification were
  removed.

## Cost

Measured on the real corpus, median of 10 exports of the 4,245 bp record.

* With a corpus lookup per export: **31.7 ms**.
* With the template already in memory: **8.3 ms**.

So the comparison is cheap and the database round trip is the cost. Caching is a
deployment choice and this package did not make it: a cache is a correctness
decision about staleness, and inventing a policy for it here would have been
guessing at a requirement nobody stated.

## Still true, and not claimed otherwise

* No external screening backend is configured. The default is a named no-op whose
  recorded result says so.
* The `retrieved_template` verification applies to plasmid spans. The other three
  capabilities' spans are registry parts, which are compared against `data/parts`,
  and user input, which has no external record by definition.
* Nine inherited tracked documents still contain em dashes, unchanged and
  previously recorded in `progress/WP-13.md`.
